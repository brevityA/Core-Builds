# Core Streams — protocol and deployment research

**Research date:** 2026-10-26  
**Implementation scope:** private Stremio stream add-on served by the existing Core Builds Cloudflare Worker.

## Findings

### Stremio's add-on contract is small enough for a Worker

The official Stremio Add-on SDK describes add-ons as HTTP services that answer a manifest and resource requests. Its stream response supports a direct stream `url` and torrent `infoHash` (with optional `fileIdx`). That means Core Streams can implement the protocol directly without running the Node SDK or a long-lived server. The add-on only needs to return metadata/stream references; the player handles playback.

- [Stremio Add-on SDK](https://github.com/Stremio/stremio-addon-sdk)
- [Official stream response reference](https://github.com/Stremio/stremio-addon-sdk/blob/master/docs/api/responses/stream.md)
- [Official SDK testing guide](https://github.com/Stremio/stremio-addon-sdk/blob/master/docs/testing.md)

### The existing proxy must remain narrow

`cloudflare-worker/worker.js` currently scopes `/proxy/*` to AIOStreams config, manifest, and stream-result routes (plus separate WuPlay and TorBox-read lanes). It is intentionally not a general URL relay. Core Streams therefore gets a distinct `/core-streams/<install-token>/...` protocol surface, and does not widen `/proxy`.

The implementation federates fixed Stremio stream add-on origins (Torrentio, TorrentsDB, and the movie-only Public Domain Movies add-on). An optional add-on can be selected only by the operator using a Worker secret; callers cannot submit a target host or URL. Upstream redirects are not followed, results are size-capped, URLs are normalized, and provider failures are isolated.

Repo evidence for the initial torrent sources is in [`tools/benchmark/addon-inventory.md`](../tools/benchmark/addon-inventory.md): it recorded the Torrentio and TorrentsDB manifests as live on 2026-09-06. That is historical evidence, not a guarantee of availability today. The sandbox cannot make direct live requests to those provider hosts, so this implementation has mock-based contract tests but **no live-provider smoke result** yet.

### Cloudflare is appropriate for bounded fan-out, not a full web-scraping engine

Cloudflare's current [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) list 50 subrequests per invocation and six simultaneous outgoing connections on Free, alongside 100,000 Worker requests/day and 10 ms CPU time per invocation. Network wait time is not CPU time, but parsing/scraping HTML and large payloads still consumes CPU and memory.

Before the widened-search integration below, Core Streams fanned out to at most three JSON add-ons (two fixed sources and one optional configured source). It now fans out to at most four (three fixed movie sources and one optional configured source), streams each response through a 1 MiB bounded reader, and applies a 5.5-second timeout. Each provider has an isolate-local circuit breaker (three failures, then a 30-second cooldown); it is deliberately best-effort, not a globally consistent outage detector. Core Streams does **not** fetch/relay video bytes. The new source's bounded lookup and sequential Archive metadata reads keep the worst case within 10 upstream requests and six concurrent connections. A future implementation that scrapes many sites directly should use a separately operated scraper backend or indexer, with the Worker serving only as a protected edge/API layer.

### Direct HTTP source status

The supplied [PenguPlay configure page](https://pengu.uk/configure) currently presents sign-in before a personal install can be created. The public page does not expose a documented unauthenticated Stremio stream API. Core Streams therefore does not hardcode or scrape PenguPlay. Instead, the optional `CORE_STREAMS_HTTP_SOURCE_MANIFEST` secret accepts a Stremio-compatible HTTPS manifest URL supplied by the operator. It is only suitable if the source's terms permit this use and its manifest URL is compatible with the route contract. The URL must not have a query string, fragment, port, userinfo, IP literal, or reserved hostname; configuration tokens may be in path segments. The integration is not yet live-verified against PenguPlay. For direct media, only HTTPS URLs are accepted; playback request headers are limited to `Accept`, `Accept-Language`, `Origin`, `Referer`, and `User-Agent`, with cookies, authorization, and fixed `Range` headers removed.

### Full-engine comparison

The research found [Magnetio](https://github.com/peterdsp/Magnetio), a recent self-hosted Stremio project whose README describes its own multi-provider torrent scraper, Torznab/Jackett/Prowlarr support, and optional debrid integrations. That is a better architectural comparator for a future truly independent Core Streams scraper. It also illustrates why that scope is materially larger than a Worker route: source adapters, indexer behavior, debrid APIs, per-user credentials, caching, configuration, and ongoing site maintenance all need owners. This implementation intentionally starts with a bounded federated add-on, not copied scraper code.

### Access and privacy

The manifest URL contains a random install token in its path, acting as a bearer credential. Use a long random token, distribute the URL only to the intended users, and rotate the secret if it escapes. The Worker code does not log request paths, tokens, upstream URLs, or stream payloads. A manifest URL should still be treated as private client data.

The existing `RL_PROXY_CUSTOM` binding and local limiter are used for stream requests. The route returns `Cache-Control: no-store` because provider results and source URLs can be short-lived. It never proxies media bytes: Stremio connects to returned HTTPS URLs itself, and torrent results use Stremio's `infoHash` protocol.

## MVP behavior

- `GET /core-streams/<token>/manifest.json` — stream-only Stremio manifest for movies and series.
- `GET /core-streams/<token>/stream/{movie|series}/{imdb-id}.json` — bounded parallel requests to Torrentio and TorrentsDB, the movie-only Stremio Public Domain Movies source, optionally one operator-configured Stremio add-on, and (movies only) the Cinemeta-backed Internet Archive/explicitly mapped Blender Open Movies sources.
- Accepts only IMDb IDs; series IDs must include `:season:episode`.
- Normalizes HTTPS stream URLs and valid 40-character torrent info hashes, removes obvious unsafe URLs, de-duplicates, and returns an empty protocol response when providers fail.
- No user configuration page, own indexer scraper, debrid resolver, catalog, playback relay, or provider credentials are included yet.

## Continued research — failure domains and fallback design (2026-10-25)

This pass focuses on the actual failure being mitigated: **TorBox being unavailable**, rather than only a Stremio add-on endpoint being down. Findings below are source-backed design guidance, not a claim that any provider is currently healthy or that a fallback has been live-tested.

### A TorBox outage can occur at several different layers

| Failure layer | What users experience | What helps | What does not, by itself |
|---|---|---|---|
| Stremio source add-on (e.g. Torrentio endpoint) | No results from that add-on | A different source/add-on endpoint | Another indexer behind the same failed endpoint |
| Torrent index/search coverage | Missing titles or poor matches | More independent indexers (deduped) | A second debrid account alone |
| TorBox API/account service | Cannot check cached availability, create transfers, or resolve links through TorBox | A separately supported debrid service, configured by the user, or raw P2P where lawful and supported | Another torrent-result add-on still resolving only through TorBox |
| TorBox delivery/CDN/region | Results appear but playback stalls/fails in a region | Another provider's delivery path, or P2P where lawful and supported | A healthy search API or a manifest-only check |
| User network/client/P2P capability | Torrent result exists but cannot play | A supported HTTPS/debrid result or a different network/client | More hashes that use the same unavailable playback path |

TorBox's official status page is useful as an operational signal, not as a test of the user's route or any individual playback link. On this research date it lists recent API, database, and regional CDN incidents/maintenance, illustrating that search/API and delivery are separate failure modes. The page is dynamic; **recheck it before acting** rather than treating this dated snapshot as current status: [TorBox status](https://status.torbox.app/) and [incident history](https://status.torbox.app/incidents).

### What the existing Core Streams MVP actually covers

Core Streams asks Torrentio, TorrentsDB, and (for movies) the Stremio Public Domain Movies add-on for stream objects and returns validated URLs/infohashes; movie lookups can also return narrowly filtered Internet Archive MP4s or exact-mapped official Blender Open Movies (Big Buck Bunny, Elephants Dream, Sintel, Tears of Steel, Glass Half, and Coffee Run). It does not send TorBox credentials, check TorBox cache state, resolve a hash with a debrid provider, or proxy playback. Therefore:

- It can be useful if the user's normal path fails at TorBox **and** the client can play a returned public HTTPS stream or P2P torrent.
- A returned `infoHash` is a torrent candidate, **not** a cached/debrid link, a guarantee of seeders, or a promise that Stremio Web/TV can play it.
- The configured HTTP-source hook can federate a compatible direct-HTTP add-on, but it does not transform P2P results into cached HTTPS streams.
- The current two built-in sources are not independent index corpora in a strong sense: prior inventory research found substantial provider overlap. Add-on count is not the same as independent coverage.

This is an intentionally separate failure domain from TorBox only at the **source-discovery and raw-P2P/direct-HTTP** layer. The Worker itself, Cloudflare egress, Stremio client, and any configured source can still be shared dependencies.

### Best-fit resilience path: AIOStreams plus a second user-owned service

AIOStreams' current setup guide says users can select more than one debrid service. Its group/stream-expression system can also filter/group returned streams by service and can invoke backup groups when earlier results are insufficient. These are useful primitives, but they are not a blanket guarantee of automatic outage failover: a second supported service must be enabled in the relevant add-on/service configuration, have working user credentials, and be covered by the chosen group's condition. Confirm that the selected template actually routes the desired sources through both services; a source add-on can support a smaller service set than AIOStreams itself.

The documentation gives examples of Real-Debrid and TorBox and lists many service IDs, but no provider has been selected for this project. Recommend that the user first choose a second provider based on price, region, current service terms, and personal preference; then test one movie and one episode with TorBox temporarily disabled in a **staging/test config**. Do not paste a debrid key into this repository or a shared Worker secret. A shared Worker-held key would make one operator account the playback credential for every Core Streams install, create account-sharing/credential exposure concerns, and still leave the user dependent on that provider's API and delivery path.

Relevant official AIOStreams docs:

- [Setup: select service(s)](https://docs.aiostreams.viren070.me/configuration/setup/) — service selection accepts the services the user has; credentials are supplied to that configuration.
- [Groups](https://docs.aiostreams.viren070.me/guides/groups/) — examples include conditions based on stream count and cached service results. Note: groups may fetch in parallel and discard pending results, depending on behavior/configuration; don't assume strict sequential failover.
- [Stream Expression Language](https://docs.aiostreams.viren070.me/reference/stream-expressions/) — supports service-aware filtering/grouping.

### Source/engine comparison for the next increment

| Option | What it adds | Operational cost / caveat | Fit |
|---|---|---|---|
| Keep current Core Streams MVP | Cheap, isolated alternate Stremio endpoint; direct HTTPS + raw torrent candidates | Depends on external source add-ons; no own indexer, debrid, status page, or persistent cache | Keep as a lightweight no-TorBox fallback, after live validation |
| AIOStreams with a second debrid service | Cached/HTTPS playback can survive TorBox-specific service failure where both the add-on and source support that service | User must separately subscribe/configure; no service is guaranteed independent or available; test actual template routes | Strongest practical fallback for dependable playback |
| Self-host Comet + Prowlarr/Jackett | Own add-on and chosen indexers; Comet project documents Torznab integration and debrid/usenet search | Requires a persistent host, database/cache and maintenance; still requires separately configured debrid for cached HTTPS results | Better if independent indexer ownership is the goal |
| Self-host Magnetio | Built-in provider scraper, Torznab/Prowlarr/Jackett and multiple debrid integrations per its project docs | Persistent database/state and active scraper operations; project-specific provider availability/terms must be reviewed | Broader standalone engine, not a Worker-sized feature |
| Add TorBox API resolution to this Worker | Could label cached results or return TorBox URLs while TorBox works | It directly reintroduces the dependency this fallback is meant to survive; requires per-user credential flow, account isolation, API/ToS review and caching | Not a TorBox-outage solution; do not prioritize |

The Comet project documents Docker/source deployment and Torznab support ([repository](https://github.com/g0ldyy/comet)); the AIOStreams project documents persistent storage and its Worker-support drop in its [v1-to-v2 migration notes](https://docs.aiostreams.viren070.me/migrations/v1-to-v2/). Magnetio's scope is described in its [repository](https://github.com/peterdsp/Magnetio). These are architectural comparisons, not recommendations to install unreviewed public instances or to supply credentials to a service without checking its operator and terms.

### Proposed verification plan before calling Core Streams a dependable fallback

1. **Do not test by adding real debrid credentials to Worker secrets.** Deploy a staging Worker with a fresh install token only.
2. Check status/manifest separately from actual stream responses; a 200 manifest proves only that the add-on answers.
3. From Cloudflare egress (or the deployed smoke path), request a known movie and an episode through each source independently; record HTTP status, duration, schema validity, error class, and whether results are direct HTTPS or infohash. Do not log full URLs, tokens, or stream bodies.
4. Compare result counts before/after deduplication and shared infohashes across sources; repeat over a small set of common and less-common titles. A duplicated provider list should not be reported as incremental coverage.
5. Install on Stremio Desktop and the actual target TV/mobile client. Test one HTTP result and one torrent result where lawful and technically supported; verify that `behaviorHints.notWebReady` and filenames behave as expected.
6. Separately exercise AIOStreams with a second user-configured service by disabling TorBox for the test configuration. Confirm which configured add-ons use that service and verify cached/direct playback rather than treating a stream-list response as proof.
7. Capture p50/p95 response time and source error rate over a representative period. Keep the current no-store behavior unless observed client behavior demonstrates a safe, useful cache policy; dynamic source links can expire.

### Protocol and platform checks from this pass

- Stremio's stream response supports either a direct URL or torrent `infoHash`; the SDK specifically requires `behaviorHints.notWebReady: true` when `proxyHeaders` is used. It also recommends `behaviorHints.filename` for URL streams so subtitle lookup can work. The current normalizer forwards a filename when supplied, but a live test should confirm providers actually supply useful values. [Official stream response schema](https://github.com/Stremio/stremio-addon-sdk/blob/master/docs/api/responses/stream.md).
- The SDK has per-handler `cacheMaxAge`, `staleRevalidate`, and `staleError` response controls. Core Streams currently returns `Cache-Control: no-store` by design, which avoids caching short-lived URLs and personalized/provider-specific results; changing this needs client tests. [Official stream handler docs](https://github.com/Stremio/stremio-addon-sdk/blob/master/docs/api/requests/defineStreamHandler.md).
- Current Cloudflare Workers limits documentation lists six concurrent outgoing connections, 50 subrequests per request on Free, 10 ms CPU per invocation on Free, and 128 MB per isolate. Three bounded source requests remain a modest fan-out; parsing/scraping broad HTML or relaying video bytes would change the risk and cost model materially. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).
- Keep playback bytes off this Worker. It returns metadata/stream references only, which avoids turning the Worker into a video relay, avoids consuming its outbound bandwidth as a player transport, and preserves the current SSRF/security boundary. Review Cloudflare's current [Developer Platform Supplemental Terms](https://www.cloudflare.com/supplemental-terms/) and [abuse approach](https://www.cloudflare.com/trust-hub/abuse-approach/) before any product expansion; this research is not a legal determination.

### Research decision

**No implementation change is justified by this research alone.** Keep the current add-on small and private; validate it live before relying on it. For cached fallback playback, prioritize a user-selected second debrid service in AIOStreams. If the future requirement is independent source ownership, evaluate a separately hosted Comet/Magnetio-style engine rather than attempting a full scraper/debrid system inside this Worker. No provider account, source integration, deploy, or live playback test was added in this pass.

### Host, source, and account are separate axes

- **Moving hosts** (for example, another MediaFusion or Comet instance) can reduce dependence on one operator's endpoint, but the same app may use the same indexers and the same debrid backend. This mainly addresses host/operator outages, not TorBox itself.
- **Adding a different add-on** (Jackettio, Magnetio, Easynews+) may add different search or transport paths, but only if the feature is actually enabled and the response is useful for the user's titles.
- **Changing debrid service** changes cache resolution and delivery. That remains a separate user credential and account relationship; do not solve it by putting one global user's token in `CORE_STREAMS_HTTP_SOURCE_MANIFEST`.
- A custom manifest URL can be a bearer secret even if its host is public. Configured manifest paths may embed API keys, usernames/passwords, provider choices, or access tokens. Treat the entire URL as credential material.

AIOStreams documentation explicitly warns that its official ElfHosted public instance disables P2P, HTTP and Live stream types, while other public instances may differ. Its public-instance page provides supported instance identities; those instances are not interchangeable in feature policy, upstream-IP/rate-limit behavior or maintenance. If the intent is to *use* more hosted add-ons, install/configure them through the user's AIOStreams setup rather than asking Core Streams to scrape one public aggregator from another. The latter adds nested fan-out and can violate rate limits or operator/developer expectations.

### Host additions to prioritize for a later decision

1. **For host redundancy only:** keep a list of stable public hosts for Torrentio/MediaFusion/Comet, but don't call them independent sources until measured. Favor separate operators and check their current official docs/status.
2. **For true indexer ownership:** a private Jackettio or self-hosted Comet/Magnetio with the user's own Prowlarr/Jackett is more meaningful than blindly adding several shared aggregators. That requires a durable host and someone to operate it.
3. **For TorBox service redundancy:** configure a separately selected debrid service on the user's AIOStreams/add-on account; choosing another host for TorBox does not replace TorBox's cache/API/CDN.
4. **For no-debrid transport diversity:** test a properly authorized direct HTTP/Usenet source (such as the user's own Easynews+ configuration) in Stremio itself. Do not forward its account-bearing config through a shared Worker installation.
5. **Do not add retired/stale projects:** KnightCrawler's former ElfHosted instance is retired and its project stopped being maintained; Annatar's public instance is also deprecated. Their old URLs should not enter the provider list simply because old guides still mention them.

### Why I am not adding these hosts to the Worker now

The current integration deliberately has a short fixed source list plus one operator-configured manifest. Adding public hosts is a protocol/security change, not just inserting URLs: provider terms/rate limits, shared-IP behavior, configured manifest path compatibility, credential exposure, result provenance, stream expiry, and host failover all need review. A configured HTTP URL may also return a personalized debrid link; sharing the Core Streams install token does not make that source configuration safe to share.

Next useful measurement is a small opt-in staging matrix across **one title/movie and one episode** per permitted host, with no credentials in logs: manifest JSON/version, stream route status and duration, result kind (HTTPS vs infohash), normalized count, duplicate hash ratio, and successful playback on the target client. Only integrate a host if it has explicit/publicly documented reuse permission or is configured solely by the individual user through a credential-safe design.

## Continued research — lawful direct-HTTPS media origins (2026-10-25)

This pass separates actual media origins from Stremio add-on hosts. A Stremio add-on `manifest.json` is a metadata/protocol endpoint; it is not itself a playable stream. By contrast, a Stremio stream object with a direct `url` points the player at the media resource. HLS `.m3u8` URLs are playlists (not single files), while an embed/player page is HTML and DRM-backed services are not raw media sources. HTTPS says nothing by itself about reuse rights, link lifetime, codec support, or availability.

- **Open Archive Stremio add-on proposal:** [Illumera PR #216](https://github.com/HereLiesAz/illumera/pull/216) describes a Cloudflare Worker add-on using curated Internet Archive collections and direct HTTP plus Archive-backed torrent links. This is a proposed pull request, not evidence of a merged, maintained or production service. It is a useful design/code-review lead, but not a source to federate without reviewing its code, merge status, license filtering, rights model, dependencies and route behavior. The claim in the PR that it was verified live is the author's claim, not an independent test in this research.
- **Stremio public-domain repository:** its `streams.json` has a single static Big Buck Bunny direct-media entry (and an HTTP URL) and was last changed in 2023. Useful as a protocol-shape example, not a current broad source or proof that the file still plays.
- **National Oceanic and Atmospheric Administration:** NOAA's collection is useful for imagery, but NOAA notes its videos often contain third-party copyrighted footage. Don't treat NOAA videos as automatically public domain; item-level rights clearance is required.
- **Smithsonian Open Access:** its API is a strong CC0 image/metadata source, but official materials focus on 2D/3D images and the API says it omits media files where rights prevent distribution; this research did not establish a sufficiently broad direct-video corpus. Exclude from the first stream-source shortlist.
- **Australian ABC/SBS archives:** ABC offers licensing or limited community-access deliveries, while ABC iview programs have time-limited broadcaster rights; SBS says it may not own rights to acquired programs. A public broadcaster's player or a direct HLS/DASH URL does not make content free to redistribute. The ABC has released some historical footage under Creative Commons through Wikimedia Commons; use those specific item records and licenses, not a broad iview scraper.
- **Commercial news footage libraries (e.g. AP):** they offer licensed media APIs but require contracts/entitlements and are not public, free stream sources. They are possible only if the user owns a suitable media license.
- **YouTube/Vimeo and similar:** a video page, an embed, or a platform `ytId` is not a direct HTTPS media file. Some official Stremio response forms can reference platform IDs, but that falls outside the current URL-only direct-media source. Use only publisher-authorized integrations; don't scrape signed URLs or bypass DRM/access controls.
- **Subscription streaming services (Netflix, Prime Video, ABC iview, etc.):** HLS/DASH may be encrypted, signed, geofenced or tied to app sessions. Do not extract or relay protected segments, defeat DRM, or treat an expiring playback URL as a reusable public stream. Use their official client/provider integration or supported discovery/WatchHub links.

### Fit with Core Streams and a TorBox outage

These origins can provide lawful direct HTTPS alternatives for a narrow, open/archival catalogue or a user's personal library. They will not provide the commercial movie/series coverage a debrid scraper aims to find, and they are not interchangeable with another debrid provider. The sensible path is an **opt-in open-media source adapter** (likely IA first, then LoC/NARA/Europeana after rights and format filters), plus a separate per-user Plex/Jellyfin integration if wanted. Keep this separate from the existing federated torrent add-ons and don't route media bytes through the Worker.

Before adding any origin, test at least: (1) API/manifest behavior from Worker egress, (2) returned URL is HTTPS and ends at a media resource rather than HTML, (3) `HEAD`/range response and redirects from an actual client, (4) video codec/container/audio codec on Stremio Desktop and target TV/mobile client, (5) matching accuracy and episode identity, (6) rights metadata/credit carried into the result and an item-level review workflow, and (7) short-lived URL behavior. The current Core Streams URL validator is a security/format guard, **not** a rights checker, allowlist, transcode service, or media-playback health check.

The earlier broad-source survey did not validate a representative media file's codecs or Stremio playback. Subsequent live API/page checks are recorded below; no video bytes were downloaded, no range request or playback test was run, and no independent legal clearance was performed. The implemented adapters are covered by mocked tests but still require deployed, client-side verification.

### Implementation update — Internet Archive adapter (2026-10-25)

At this stage, Core Streams performed a bounded movie lookup against Cinemeta and Internet Archive, in parallel with the existing torrent add-ons, and checked the official Blender Open Movies PeerTube channel for two explicitly mapped films (Big Buck Bunny and Elephants Dream). The later Blender mapping extension is documented below. The Archive adapter only returns direct HTTPS `.mp4` file URLs when it can confirm an exact normalized title, an exact matching year, and an explicit item-level `licenseurl` allowlisted to CC0, Public Domain Mark, CC BY, or CC BY-SA. It rejects series, other file formats, title/year mismatches, missing/unsupported license declarations, private files, unsafe identifiers/path segments, and CC BY-NC/ND licenses. It caps candidate metadata fetches, response bytes, timeouts, and returned variants. Results carry the archive item URL, creator, uploader-declared license and a warning that the rights statement has not been independently verified. Cinemeta, Internet Archive, and Blender source failures are isolated by their own best-effort per-isolate circuits, so one source failure does not suppress results from the others.

This does **not** mean Internet Archive guarantees rights or that the MP4 is compatible/playable. The Archive says rights claims on item pages are not guaranteed; this adapter's license filter is only a conservative discovery filter. The Internet Archive's own Movies and Videos guidance also specifies playback requirements for original MP4s (H.264 video, AAC audio, `yuv420p`, and the `moov` atom at the beginning); Core Streams does not inspect those media bytes or infer codecs from an `.mp4` suffix. The integration also cannot cover episodic media or broad current commercial catalogues. Verify each candidate and client playback before relying on it. No media bytes, codec probe, range request or Stremio playback test has been run. Details and fixtures are in `cloudflare-worker/core-streams.js` and `cloudflare-worker/core-streams.test.js`.

The adapter intentionally does **not** hardcode the public Comet, MediaFusion, Jackettio, Magnetio or Easynews+ hosts found in the earlier manifest inventory. Manifest retrieval alone did not establish reliable stream results, independent source coverage, reuse permission, or credential-safe operation; some require personal configs/debrid/Usenet accounts and public services can restrict P2P/HTTP. The existing operator-configured add-on hook remains available when the operator independently confirms a source is compatible and authorized. LoC, NARA, Europeana, NASA, Commons, general PeerTube federation and personal Plex/Jellyfin remain unintegrated because source rights, matching, format/client behavior or per-user credential constraints were not sufficiently established for automatic shared-worker federation. At that earlier point, the official Blender Open Movies PeerTube origin was integrated only for Big Buck Bunny (`tt1254207`) and Elephants Dream (`tt0807840`), using exact mapped title/year plus official channel/account and direct MP4 URLs. Big Buck Bunny's PeerTube record declares Attribution and its official project page confirms CC BY 3.0. Elephants Dream's exact public PeerTube record reports an unknown license, but the official Blender project site explicitly states the movie is CC BY 2.5; the implementation therefore accepted unknown PeerTube license metadata only for that statically mapped title and exact allowed upload title on the official channel/account. This was not a general PeerTube indexer; Sintel and Tears of Steel were added in the follow-up below.

Live source checks confirmed that the Blender PeerTube search returns Big Buck Bunny records and a corresponding detail record with direct MP4s; the official Big Buck Bunny page confirms CC BY 3.0. The exact official Elephants Dream PeerTube record (`/api/v1/videos/55`) is public, owned by account `blender`, on channel `blender_open_movies`, has a direct 720p HTTPS MP4 with audio/video flags and duration, but its PeerTube licence field is `Unknown`; the original Blender project site explicitly licenses the movie under CC BY 2.5 and sets credit requirements. Code is deliberately restricted to the two known IMDb ID/title/year tuples, the exact official channel/account and per-film allowed video titles; it does not use general PeerTube search results or infer a license for other channel content. Mock tests verify the filters, but no MP4 bytes were fetched and no Stremio playback/codec test was done.

### Deeper source verification and implementation hardening (2026-10-25)

- **Internet Archive playback caveat:** the official [Movies and Videos guide](https://help.archive.org/help/movies-and-videos-a-basic-guide/) says an original MP4 must use H.264 video, AAC audio, `yuv420p`, and place the MP4 `moov` atom at the front for the Archive's online player; it may derive an `.ia.mp4` when the original does not meet this. Core Streams currently validates metadata, file extension, format label, visibility, license declaration, filename path, and size only. It does not inspect media bytes or prove Stremio codec compatibility. This is now explicit in the implementation documentation; do not present `.mp4` as a playback guarantee.
- **Prelinger collection:** the official [Prelinger rights FAQ](https://www.panix.com/~footage/prelarch.html) expressly warns that not all collection works are public domain or Creative Commons; the [Internet Archive collection record](https://archive.org/details/prelinger) points users to item-level rights information. This supports the existing rule to require an item-level allowlisted license URL, not an `identifier`/collection name heuristic. This is a collection within the already implemented Internet Archive provider, not an additional independent API.
- **Library of Congress National Screening Room:** live queries to the public [LoC JSON API](https://www.loc.gov/apis/json-and-yaml/) showed the collection endpoint returns structured records with direct MP4 `resources[].video`, HLS `video_stream`, and an `access_restricted` flag. A query for “Great Train Robbery” matched the right 1903 item, while an earlier broad Apollo 11 query matched unrelated “Apollo’s Fire.” Importantly, LoC says the collection includes both copyrighted works shown by special permission and public-domain/no-known-restriction works; the collection's [Rights & Access notice](https://www.loc.gov/collections/national-screening-room/about-this-collection/rights-and-access/) asks users to consult item-level records and notes privacy/publicity, licensing, trademark and foreign-rights issues. `access_restricted:false` only showed access was not blocked; it did not establish reuse rights. We therefore do not emit LoC media URLs until a machine-readable per-item rights rule can be demonstrated and tested.
- **NASA:** the public [Images API documentation](https://images.nasa.gov/docs/images.nasa.gov_api_docs.pdf) exposes `/search` and `/asset/{nasa_id}` and returned video metadata/asset manifests in the earlier probe. The checked asset manifest included MP4 entries using HTTP URLs, which Core Streams intentionally rejects. NASA's [media guidance](https://www.nasa.gov/nasa-brand-center/images-and-media/) also reserves its insignia/identifiers and says third-party material may be present. Search results for “Apollo 11” are clips/mission assets, not evidence of a matching feature film. No NASA adapter is justified by this evidence.
- **NARA:** official [permissions guidance](https://www.archives.gov/research/motion-pictures/permissions) says some federal-government-produced work is public domain, but donated/private materials and records with copyright, contract, deed, publicity or other restrictions may also be held, and NARA does not make a definitive item rights determination. The attempted catalog endpoint did not yield machine-readable JSON through the page-fetch surface. This remains a research lead, not an implementation candidate.
- **Implementation changes from this pass:** IA year matching is now strict (not ±1), avoiding year-neighbor false positives. IA item-metadata failures and Blender detail failures now count toward their own source circuits rather than being reset by a successful search response. Tests cover exact-year rejection, an IA metadata failure opening its circuit, and the narrowly mapped Elephants Dream record. At that earlier point, the Blender map included Big Buck Bunny and Elephants Dream only; the latter's official source page declares CC BY 2.5, while its PeerTube metadata was unknown, so acceptance was a narrowly scoped static exception backed by that canonical project-rights page. The later two-title expansion is described in the follow-up below.

Sources consulted for the current audit: [LoC National Screening Room API results](https://www.loc.gov/collections/national-screening-room/?q=Great%20Train%20Robbery&fo=json&c=5), [LoC rights/access](https://www.loc.gov/collections/national-screening-room/about-this-collection/rights-and-access/), [NASA API docs](https://images.nasa.gov/docs/images.nasa.gov_api_docs.pdf), [Prelinger rights FAQ](https://www.panix.com/~footage/prelarch.html), [Blender Elephants Dream project](https://orange.blender.org/), and the live [Blender PeerTube record 55](https://video.blender.org/api/v1/videos/55). These are source research results, not a rights opinion or Stremio playback certification.

### Open and public-domain film discovery

- **WikiFlix** ([official site](https://wikiflix.toolforge.org/), [Wikidata help page](https://www.wikidata.org/wiki/Help:WikiFlix)) is a useful browser-first catalog of films identified in Wikidata as public domain, with linked media on Wikimedia Commons, Internet Archive, or YouTube. The help page says the database is community-maintained and updated hourly, and that only a fraction of public-domain film records have a linked video. Use WikiFlix to discover a candidate, then inspect the actual source file, its item-level rights/territory, and its player/codec. Public-domain status can be jurisdiction-specific; Wikidata assertions and availability of a file are not independent legal or playback verification. Some records lead to YouTube rather than a direct MP4.
- **Internet Archive** remains the most practical broad open-archive lane already integrated, but the uploader-declared license is not independently verified. Its existing adapter enforces exact title/year, allowlisted license metadata, direct MP4, and exposes a rights warning; it is not a general guarantee of lawful use or successful playback.
- **Wikimedia Commons** can supply direct video files and license/attribution metadata. Metadata is incomplete for some files and formats are often WebM; a curated file allowlist is safer than broad automatic title matching.
- **Blender Open Movies** are good openly licensed short/feature animation examples. At the time of this earlier source review, Core Streams had exact mappings for Big Buck Bunny and Elephants Dream only. Sintel, Tears of Steel, Spring and Sprite Fright were still candidates pending verification; the later 2026-10-25 follow-up below verifies and adds Sintel and Tears of Steel. Spring remains unintegrated because its PeerTube record uses a version-unspecified Share-Alike label, while the project page names CC BY 4.0; the posted media terms are therefore not sufficiently clear to encode, while Sprite Fright was not live-checked for an exact direct-stream/rights path.
- **Australian government/archival footage** can be a legitimate substitute when the aim is factual/history/nature viewing rather than mainstream entertainment. National archives, the NFSA and official agency libraries have mixed access and rights; check each item, not the institution brand or file extension.

### API candidates: not yet safe/reliable enough to integrate

**DVIDS (U.S. Department of Defense public media)** is the most promising newly discovered API for military/government footage, briefings, documentaries and news assets—not for mainstream studio films. Its [API docs](https://api.dvidshub.net/docs) describe a library of 1.8 million assets; the [search endpoint](https://api.dvidshub.net/docs/search_api) can search video and filter results, while the [asset endpoint](https://api.dvidshub.net/docs/asset_api) may return MP4 files and an HLS URL. A developer API key is required. Credit is requested, and exact asset restrictions/rights must be checked. There is an important terms nuance: the API terms say API media/info is free for commercial use, while DVIDS' general [copyright page](https://www.dvidshub.net/about/copyright) says some items can carry third-party rights and describes limits for certain uses; the per-asset notices still matter. Its API terms also prohibit disclosing credentials (except to confidential agents), using another entity's credentials, and masking usage. Before adding it to a shared or publicly installable Worker, confirm the intended end-user/API-client arrangement with DVIDS. If ever tested, the key belongs in a Worker secret, never source code, a manifest, logs, or returned stream URL; do not rewrite/relay DVIDS links against its terms. A free key and API docs alone are not enough to call the source integrated or reliable.

**NPS multimedia API** exposes a `multimedia/videos` endpoint and requires a free API key ([official API docs](https://www.nps.gov/subjects/developer/api-documentation.htm), [get started](https://www.nps.gov/subjects/developer/get-started.htm)). NPS has at least some directly downloadable public-domain H.264 footage: the official Yosemite stock-footage page explicitly says the footage may be used for any purpose. But the NPS usage guidance says only media credited to NPS without a copyright symbol is public domain; material with a copyright mark or another credit must not be presumed public domain. This is a narrow educational/nature/park-video source, not feature-film coverage. No API key, live API call, returned-file compatibility or Stremio playback has been tested.

Both API candidates have real potential for a **separately opt-in, narrowly scoped factual-video lane**. To qualify, test API key authorization and key secrecy, item-level rights/credit/restrictions, title matching, direct media status/Range, format and codec support on target clients, API quotas/terms, and key ownership. Keep the key owner in control; do not make either a blanket public Worker integration on the basis of docs alone.

### Workarounds when the title is not in Core Streams

1. **For ordinary current films/series:** check Freeview, SBS, ABC iview, Tubi, 7plus, 9Now, 10 and Brollie directly; try WatchHub or another supported where-to-watch catalog for discovery, then open the authorized provider app/site. Availability is title- and region-specific. WatchHub links are discovery/deep links; they do not remove account, ad, rental, subscription, or territory requirements.
2. **For independent/classic films:** search Kanopy/Beamafilm through the local library, NFSA Player, WikiFlix, IA, and official open-film channels. Follow the link to the hosting source and use its own player unless the item is a verified, compatible direct file already returned by Core Streams.
3. **For owned media:** use a private Jellyfin/Plex server or local-library add-on with only the user's authorized files. Keep the server credential and URL private, use HTTPS or a trusted private network, and configure a per-user Stremio bridge. This can cover material the user already owns but does not create broader public access.
4. **For TorBox resilience specifically:** configure a second independently selected debrid service in the user's AIOStreams setup. Validate the actual add-ons, cached links and playback with TorBox disabled in a test configuration. A raw torrent/magnet result is not equivalent to a cached HTTPS link and may not work on the target client/network.
5. **Do not work around DRM or rights controls:** don't extract/replay signed HLS/DASH segments, scrape subscription APIs, share a personal service token, or proxy another person's credentials through the Worker. Choose official apps, authorized deep links, user-owned media, or properly licensed direct files.

## Free add-on stream formats and safe integration (2026-10-25)

### Implementation details

- `normalizeStream` now accepts Stremio-native `ytId` values only when they match `^[A-Za-z0-9_-]{11}$`; malformed IDs, YouTube webpage URLs, and `externalUrl`-only entries remain rejected.
- `dedupeKey` now de-duplicates identical YouTube IDs across configured and fixed add-on responses.
- The optional `CORE_STREAMS_HTTP_SOURCE_MANIFEST` add-on route is the integration point. It can federate an add-on that supplies `ytId`, direct HTTPS, or torrents, subject to its path-form manifest URL fitting the existing safety guard. No YouTube API key, YouTube search scraper, new public provider host, or YouTube media relay was added.
- Treat the configured source manifest as a shared secret: it is used for every request through the Core Streams install token. Do not configure a personal YouTube API key or other account credential on an install shared with people who should not use that account. A self-hosted YouStream instance must satisfy the same isolation and its own YouTube API/terms requirements. No YouStream server, API key, video matching corpus or actual client playback was available/tested here.
- Version bumped to `0.2.2`; tests cover supported native IDs, malformed-ID rejection, source labeling and duplicate suppression. Core Streams remains undeployed.

### What was deliberately not implemented

I did not scrape `yt-dlp`, open directories, unofficial embed sites, or generic torrent indexers to find copyrighted titles. I did not copy a public add-on's private-config manifest, debrid tokens, or transient signed URLs. I also did not import the old public-domain lists wholesale: a claimed “free” label or a source add-on's availability is insufficient without current source rights, title matching, file behavior and codec evidence. For the same reason, the existing open-source adapters remain narrow and item/title filtered.

## Deep survey — free streaming services and Stremio HTTP add-ons (2026-10-26)

### Scope and confidence

“All” free stream services and community add-ons is not a finite, stable inventory: catalogs, provider lists, domains, and public instances change frequently. On the current community directory snapshot, the `http streams` category alone reports **224 results**. This is therefore a dated landscape map and primary-source audit of the material candidates surfaced in broad searches—not a claim that every one of those 224 has been individually audited. Directory descriptions, stars, version labels, and “reachable” manifest checks are discovery/availability signals, not evidence of authorization, security, or a playable result. No candidate in this section was installed, given account credentials, or playback-tested.

Stremio's [terms](https://www.stremio.com/tos) distinguish Stremio-developed Official Add-ons from independently made Community Add-ons and state that community developers are responsible for content legality and consequences. This is central to the audit: a Stremio-compatible manifest only implements a protocol; it does not license a film or grant permission to scrape, rehost, embed, or share a service's login.

### PenguPlay: what is actually verified

The [PenguPlay public site](https://pengu.uk/) currently asks the user to sign in to create a **personal** install and offers a Google or access-token path. The current [community-directory record](https://stremio-addons.net/addons/penguplay), checked 2026-10-26, reports version 1.4.0, updated 2026-10-13, and a reachable manifest; its stated function is configurable provider/quality selection for films and series. The site's publicly rendered page does not expose an unauthenticated general stream endpoint or a complete, durable provider/rights inventory. The linked install flow is thus user-bound, rather than a static public source endpoint Core Streams can responsibly assume.

The developer's own 2026 Reddit update posts describe anti-scraping controls, authentication to deter automated abuse, and stream links protected by one-time, requester-IP-bound tokens; later posts name providers including 2Peckle, Cinejoy, MovieBox, 4KHDHub, MoviesDrive, VegaMovies, and Aether. These are **developer self-reports on Reddit**, not a stable API contract, independently audited privacy policy, or licensing evidence. The current visible configure page says Google verifies the account and claims the add-on stores an anonymous Google ID, but the implementation/storage claim has not been independently verified. This review did not find first-party rights grants for those upstream provider catalogs. The service may be useful as a personally installed no-debrid HTTP option when it works, but it is not a rights-cleared, public source to copy into the shared Core Streams Worker. IP-bound short-lived URLs also make server-side re-fetching or re-serving particularly inappropriate and potentially nonfunctional. Treat any personal install URL as a secret; do not send a Google token, access token, or generated manifest URL to Core Streams or another shared host.

### Why free official services are not Worker adapters

First-party terms explain the distinction clearly: ABC iview requires use through iview, restricts use to personal/non-commercial use, and prohibits bypassing technical protections; SBS prohibits reproducing, redistributing, framing or deep-linking its material absent consent; 10's terms prohibit automated crawlers/spiders and unauthorized reproduction/redistribution; Brollie and Kanopy grant personal, territorial/non-transferable viewing rights. Even a free-to-watch service can have title-specific licensing, geo restrictions, accounts, ads, expiring signed URLs, and DRM. Core Streams should not scrape pages, copy cookies, extract tokens, defeat DRM/geo checks, or create an unofficial Stremio proxy for those services absent an authorized public API/partner permission.

### Practical conclusions for the TorBox-outage goal

1. **For legal mainstream film/TV in Australia, “free in Stremio” is not a real universal alternative.** Check ABC iview, SBS On Demand, 7plus, 9Now, 10/Pluto FAST, Brollie, Tubi, Plex and the user's library apps directly. Availability is title- and region-dependent.
2. **For no-debrid direct HTTP add-ons, PenguPlay and its peers are separate third-party services**, not a license-cleared source pool. They may work on some titles but depend on changing upstream websites, personal installs, auth, quotas, IP binding and upstream link health; “works” is not guaranteed by a reachable manifest.
3. **For actual Core Streams implementation, stay with allowlisted rights-evidenced sources.** Current implementation is four LOC films and six Blender films, in addition to the previously configured add-on/torrent sources. Continue adding only exact-match items after rights and direct-media checks; do not generalize from a collection label or a stream site's “free” claim.
4. **Never place a user's PenguPlay/FEBBox/other cookie, OAuth token, private IPTV credentials, or personal manifest URL in a shared Worker secret.** Stremio add-ons are remote HTTP services: the addon operator sees the request and the final stream host sees the playback connection. HTTPS secures a network hop; it does not establish content rights or a trustworthy operator.
5. No provider from this 2026-10-26 sweep was added to code. **No deployment or playback test occurred.** The implementation and last validated manifest remain 0.6.0 with the prior 109 passing unit tests; new work here is research documentation only.

## Smarter result selection (2026-10-26)

A follow-up code review found a result-cap bug: Core Streams concatenated provider groups in fixed order and stopped at 80, so Torrentio plus TorrentsDB could consume the entire cap and hide later results from Public Domain Movies, an optional source, and the curated open-media lookups. Manifest version is now **0.7.0**. The selection order now (a) ranks each provider's returned cards by visible resolution hints, seed-count hints, release labels, and direct-play/YouTube availability, (b) places the single highest-scored first result first, (c) interleaves the remaining per-provider lists, then (d) de-duplicates and applies the cap. This gives other configured providers a chance to surface even when an earlier source returns many cards.

These signals are derived only from the provider's own display text and stream fields. They are unverified heuristics: a stream can be mislabeled, the torrent can have no live peers, or a direct URL may fail in the client. Unknown-quality results remain as lower-confidence fallbacks; no media bytes are probed and no playback is promised. Added tests cover resolution/seeder ordering and verify that a provider returning 40 links cannot starve the later sources. Existing security boundaries, source rights decisions, provider fan-out, limits, and no-media-relay architecture are unchanged.
