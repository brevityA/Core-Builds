## Configurator v2.99 (Aug 27 2026)

<CardGroup cols={2}>
  <Card title="CoreSpeed engine v3, and an apology for v1 and v2" icon="sparkles">
    if the old speed test disagreed with TorBox's own site, that was our methodology, not the CDN. Three faults, all fixed. The read loop ran on the main thread while the map, table and canvas redrew every 250 ms, so on a weak device the UI starved the download and the tool reported that starvation as your speed; every byte is now counted inside a dedicated Web Worker the UI cannot touch. The 10-second cap on the 100 MB file collapsed to roughly one second of mostly TCP slow-start on a fast line, and measured a partial file on a slow one; v3 uses a 15-second window on the 1 GB file anchored at the first byte. And a single throttled sample used to define the result; each node is now measured twice and ranked by the median of steady-state, with rep-to-rep spread shown as a Consistency column.
  </Card>
  <Card title="Two of the CDN nodes in the old build no longer existed" icon="bolt">
    TorBox renamed store-039 to store-011 (wnam) and nexus-083 to nexus-244 (latm), and the shipped snapshot still named the dead pair. v3 carries the current list and probes every endpoint on load rather than trusting it, flagging the badge as unverified when probes fail.
  </Card>
  <Card title="Three modes, and the default is the one to trust" icon="shield-check">
    Accurate runs sequentially on one connection for playback verdicts, Express samples the closest node plus the top four by ping in about two minutes, and Capacity race opens up to eight real Range connections per node. Capacity numbers are pipe capacity and never earn a playback verdict. The 12 GB budget skips nodes rather than truncating a measurement, because a truncated sample is a wrong number while a skipped node is an honest gap.
  </Card>
  <Card title="Known gap: v3 has not been confirmed on a Fire Stick or Android TV" icon="sliders">
    worker isolation is the entire point of the rewrite and low-power webviews are where it should matter most, but that needs real hardware and has not been run there yet. If you have one, a test result would be worth more than another round of ours.
  </Card>
  <Card title="CoreSpeed has tests for the first time" icon="gauge">
    27 offline unit tests, 51 live assertions that run the shipped worker verbatim against a real CDN node rather than a mock of it, a syntax gate on the page, and a nightly CI run so an endpoint or engine break surfaces the day it happens.
  </Card>
</CardGroup>

## Configurator v2.96 (Aug 19 2026)

<CardGroup cols={2}>
  <Card title="CoreSpeed, a TorBox CDN speed test" icon="sparkles">
    measures all 17 Hyperdrive nodes and tells you which one to be on. It tests them the way a player actually streams: one node at a time, over a single connection, capped at 10 seconds each (~75 to 180 seconds for the full set). Ping is the trimmed mean of 5 HEAD requests. Live gauge and sparkline while it walks the list, then a ranked table, world map, and a per-region verdict on what each node can really stream for you (4K Remux down to SD, with 15% headroom) — and because latency is measured honestly, a node above 250 ms cannot earn a 4K verdict no matter how fast it downloads. Last 15 runs are kept locally with change-vs-previous columns; export as Markdown, CSV or JSON. Find it at tools/speedtest/ or from the Builder splash under Utilities.
  </Card>
  <Card title="Sequential is the default, and it is the mode to trust. Burst, Quick and Full run every node at once with several streams each" icon="bolt">
    that measures how much pipe you have, not what a stream will do, because parallel connections mask latency and a fast-ramping node steals bandwidth from its neighbours during the race. Those modes are labelled capacity races and deliberately produce no playback verdicts. Quick pulls 100 MB per node and Full pulls 1 GB, so a Full run moves real gigabytes; there is a hard 12 GB budget and an instant Stop for exactly that reason. No account, no API key, and no Core Builds backend: the measurement runs in your browser and results stay there.
  </Card>
  <Card title="If a run ever looks wrong" icon="shield-check">
    a far-away node winning, or results that disagree with TorBox's own site — re-run in Sequential mode first, then use the ⛨ Diagnostics button and share the JSON it downloads. It carries per-node pings, every round, DNS records and your ISP/ASN, which is what the crew needs to tell a routing quirk from a bug.
  </Card>
  <Card title="The proxy lane was opened narrowly" icon="sliders">
    TorBox's API sends no CORS header, so CoreSpeed fetches the CDN list through the Core Builds worker. That worker forwards any Authorization header a caller sets, which the WuPlay lane depends on, and allowing TorBox under those rules would have turned it into an authenticated relay for a service where you hold your own account key. It is scoped instead to that single public read, with credentials stripped and every other path and method refused — verified against the deployed worker rather than assumed.
  </Card>
</CardGroup>
