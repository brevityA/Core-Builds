## Configurator v3.0 (Sep 1 2026)

<CardGroup cols={2}>
  <Card title="4K builds now sort by resolution first, and that is a real change to what you see" icon="sparkles">
    until now a 1080p REMUX with a high score could sit above a 2160p file, because AIOStreams compares sort rules in order and the first rule that differs decides the whole ranking. Cached status, expression matches and score all came before resolution, so a well-scored 1080p won before resolution was ever consulted. In a 4K profile every 2160p result now outranks every 1080p result regardless of bitrate, quality label or score, and the old quality ordering still applies inside each tier. This is not a UI reorder: it changes the sortCriteria your instance actually evaluates, so it takes effect on the host, not just in the list you see here. It applies to the 4K, Mixed and Ultrawide profiles only. If you are on the 1080p profile there is nothing to reorder: that profile excludes 2160p and 1440p outright on Stable and Balanced, so no 4K reaches the sort in the first place, and this release will not bring it back \u2014 switch to Mixed \u00b7 Adaptive if you want 4K when it exists.
  </Card>
  <Card title="The trade-off, stated plainly: an uncached 2160p now outranks a cached 1080p. Putting resolution first switches off AIOStreams' separate cached and uncached ordering, which only applies when cached is the first rule. Cached sits third, so cached still wins between two files of the same resolution" icon="bolt">
    but if you would rather have instant playback than the higher tier, pick the 1080p profile or turn on Quality first. Both are unchanged and still cached-first.
  </Card>
  <Card title="1440p was being ranked below 720p in every 4K build" icon="shield-check">
    the 4K preference list named 2160p, 1080p, 720p and Unknown but omitted 1440p, and AIOStreams scores an unlisted resolution as negative infinity. Any 1440p file therefore sorted beneath everything else instead of just under 4K. It is now listed in its proper place. If you use a 1440p display or grab 1440p releases to save bandwidth, this is the fix you noticed was missing.
  </Card>
  <Card title="Options your instance will not accept are now disabled before you pick them, with the reason on the option" icon="sliders">
    on the ElfHosted community instance that means Torrentio, AnimeKitsu, Torrent Catalogs, P2P and HTTP appear greyed out and unselectable rather than being silently dropped later. Core Builds checks the host you selected, falls back to a stored capability list when the browser cannot reach it, and applies the same check to the exported JSON and the direct install, so neither can carry something the target host rejects. A Host Compatibility panel lists what was blocked, what was removed from your export, and anything kept that might still be refused.
  </Card>
  <Card title="Restricted hosts strip custom regex, and now you are told so" icon="gauge">
    ElfHosted runs with regex filtering limited to a published allowlist, and sending a pattern outside it makes the instance reject the entire save, not just that rule. Core Builds removes unlisted patterns before export and names each one. Synced regex sources are a separate allowlist and are treated separately: the Vidhin ranked-regex feed is on ElfHosted's allowed list, so it stays. On a host we cannot verify, nothing is removed and the panel flags what may be refused instead.
  </Card>
  <Card title="The generated config is now built from a specific AIOStreams release rather than a moving target" icon="wand">
    pinned to v2.33.2 and regenerated by a script that proves the commit is the one that release tag points at. Six settings Core Builds had been emitting for a while turned out not to exist in AIOStreams at all and were being discarded on arrival: maxResults, maxResultsPerResolution, seadexBestOnly, excludedStreamSources, enhanceResults and minSeeders. They are gone from the output. excludedStreamSources is replaced by excludedStreamTypes, which the instance does read.
  </Card>

TorBox-hosted AIOStreams has no readable status endpoint, so its capabilities are marked unverified and you will be asked to confirm the host. ## Configurator v2.99 (Aug 27 2026)

<CardGroup cols={2}>
  <Card title="CoreSpeed engine v3, and an apology for v1 and v2" icon="sparkles">
    if the old speed test disagreed with TorBox's own site, that was our methodology, not the CDN. Three faults, all fixed. The read loop ran on the main thread while the map, table and canvas redrew every 250 ms, so on a weak device the UI starved the download and the tool reported that starvation as your speed; every byte is now counted inside a dedicated Web Worker the UI cannot touch. The 10-second cap on the 100 MB file collapsed to roughly one second of mostly TCP slow-start on a fast line, and measured a partial file on a slow one; v3 uses a 15-second window on the 1 GB file anchored at the first byte. And a single throttled sample used to define the result; each node is now measured twice and ranked by the median of steady-state, with rep-to-rep spread shown as a Consistency column.
  </Card>
  <Card title="Two of the CDN nodes in the old build no longer existed" icon="bolt">
    TorBox renamed store-039 to store-011 (wnam) and nexus-083 to nexus-244 (latm), and the shipped snapshot still named the dead pair. v3 carries the current list and probes every endpoint on load rather than trusting it, flagging the badge as unverified when probes fail.
  </Card>
  <Card title="Three modes, and the default is the one to trust" icon="shield-check">
    Accurate runs sequentially on one connection for playback verdicts, Express samples the closest node plus the top four by ping in about two minutes, and Capacity race opens up to eight real Range connections per node. Capacity numbers are pipe capacity and never earn a playback verdict. The 12 GB budget skips nodes rather than truncating a measurement, because a truncated sample is a wrong number while a skipped node is an honest gap.
  </Card>
  <Card title="Known gap: v3 has not been confirmed on a Fire Stick or Android TV" icon="sliders">
    worker isolation is the entire point of the rewrite and low-power webviews are where it should matter most, but that needs real hardware and has not been run there yet. If you have one, a test result would be worth more than another round of ours.
  </Card>
  <Card title="CoreSpeed has tests for the first time" icon="gauge">
    27 offline unit tests, 51 live assertions that run the shipped worker verbatim against a real CDN node rather than a mock of it, a syntax gate on the page, and a nightly CI run so an endpoint or engine break surfaces the day it happens.
  </Card>
</CardGroup>

## Configurator v2.98 (Aug 26 2026)

<CardGroup cols={2}>
  <Card title="Three official Nuvio badge packs, paste-ready" icon="sparkles">
    core-neon-universal (55 badges, works on any Nuvio source), core-neon-enhanced (the same 55 with invisible AIO markers, paired with the companion formatter) and core-nodv-universal (54 badges, Dolby Vision removed for Samsung and TCL panels). All three carry the same six groups: resolution, quality, visual, audio, channels, codec. You no longer have to build a pack to get Core badges. They are generated from the Badge Builder rather than hand-written: re-running the publisher reproduces all three byte-identically, and every one of the 164 badge images resolves to the Core Builds assets path.
  </Card>
  <Card title="Groundwork, not yet switched on" icon="bolt">
    language packs for PT-BR, ES, FR, DE, IT, NL, AR and HI; named capability profiles for Fire TV Stick HD, Fire TV Stick 4K Max, TCL Google TV and Hisense; a two-seat household picker; named AllDebrid, Premiumize and EasyDebrid store presets; and an English kids overlay with a WuPlay home plan. None of these is wired into the builder yet: the two new TV profiles are not selectable, the modules are imported by nothing, and no new template JSON has been generated. Nothing you can observe in the app has changed. They are listed here so the next release, the one that turns them on, is not the first you hear of them.
  </Card>
  <Card title="Fire TV Stick 4K Max is capped, not Apex" icon="shield-check">
    it is a 4K device that stutters on REMUX-first ranking, so it gets a bitrate ceiling instead of the Apex path. TCL and Hisense join ONN and Samsung on the No-Dolby-Vision path, because neither panel family should be assumed Dolby Vision capable.
  </Card>
  <Card title="Real-Debrid still has no named preset" icon="sliders">
    its May 2026 WEB-DL filter means a named RD template would misrepresent what the service actually returns, so the preset is refused rather than shipped with a caveat.
  </Card>
</CardGroup>
